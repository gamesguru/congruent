› wire semantics? optimal storage path?


• Yes.

  Wire semantics
  This means the exact protocol behavior on the HTTP boundary, not just “it compiles and returns something.”

  In this case, the remaining wire semantics are things like:

  - frame_negotiation: true must return a real negotiated frame when possible, not just exact-match-or-fail.
  - scope: "resolved_state" and state_at need actual state-resolution behavior, not just pass-through fields.
  - sketch_status needs to follow the MSC rules precisely for decoded vs capacity-exceeded vs not-applicable.
  - inline_pdus, if supported, must be included and validated exactly as the proposal says.
  - Error behavior for invalid frames, invalid request ordering, length mismatches, and expired frames needs to match the contract, not just “some error.”

  So “wire semantics” = the public protocol contract in src/api/server/room_reconciliation.rs, especially the edge cases the peer can observe.

  Optimal storage path
  This means how the server keeps the reconciliation data internally so it does not rebuild it on every request.

  Right now the code builds room algebraic state by scanning the timeline each time. That is correct but not optimal. The better storage path would be something like:

  - maintain a per-room resident reconciliation kernel
  - maintain a sorted h64 index for bucket extraction
  - update both incrementally when PDUs are inserted or removed
  - cache them by room ID or frame ID, with invalidation on timeline changes

  So “optimal storage path” = the internal data structure and update flow that makes room_digest and room_diff cheap instead of recomputing from the full timeline every time.

  In short:

  - wire semantics = what the peer sees and what the endpoint guarantees
  - optimal storage path = how continuwuity stores and updates the reconciliation state internally
