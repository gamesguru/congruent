How much goes to roots
rezzy persists nothing — no SQL/DDL anywhere in src/. It returns created: Vec\<(StructuralHash, Vec\<u8\>)\> (the depth+1 path-copy spine) and lets the caller store it. One root per state group everywhere:

sithnapse	4	\~4,340	2× full MTHR (\~2,127 B each) + 32 B alias + 8 B refcount
congruent	4	\~2,240	3× 64 B RootHandle pointer + 2048 B lattice
96% of every root record is the 2048-byte LtHash lattice. That's not incidental — state\_group\_id = BLAKE3(lattice) (hash.rs:148) and LtHash is homomorphic, so incremental updates need the retained lattice, not just the 32-byte digest. The lattice cost is inherent to the design.
What's actually wrong
1\. congruent rebuilds the whole tree per incoming state event. This dwarfs everything above. upgrade\_outlier\_pdu.rs:239 → resolve\_state() → build\_hamt\_root\_handle → persist\_node\_recursive (resolve\_state.rs:89-97) re-materializes the entire HAMT from a flat HashMap and writes all of it, instead of using the persist\_mutation path-copy that exists and is only reachable from locally-generated events.

And put\_node (store.rs:125-135) writes two records per node (value + mtime) with no existence check — so content-addressed nodes that are byte-identical to what's already on disk get rewritten anyway. Dedup is defeated on every rebuild.
2\. sithnapse stores the same2 KB lattice twice. mtxdb\_syn.rs:565-585 writes the MTHR blob under root\_node\_id(state\_group) and state\_group\_root\_node\_id(state\_group\_id) — identical bytes, two keys (value.clone() vs value). 3\. sithnapse has no read-before-write short-circuit. It does three reads (:596, :618, :634) but uses them only for collision detection and refcount arithmetic — never to compare against value and skip. So records A and C are rewritten byte-identically on every call.

The central diagnosis is right: the dominant problem is congruent rebuilding and rewriting the full HAMT for every incoming state event. The existing path-copy spine is the obvious fix, reducing writes from hundreds of KB/MB to a few KB.

1. Change congruent’s incoming-event path to use `persist_mutation` rather than `build_hamt_root_handle` \+ recursive full persistence.
2. Add content-existence checks or make `put_node` truly content-addressed/idempotent.
3. Remove the duplicate congruent `roomid_roothandle` write.

This is the exact vulnerability the corroboration tier exists to close — a rogue origin can flood-evict a target's history today, with none of the anti-gaming protection we spent most of this session building. This is the single biggest gap.
2. No provisional/permanent notary two-tier binding. add_signing_keys treats direct fetches and notary relays identically for First-Seen-Wins purposes — there's no "provisional until direct-confirmed" staging, no override rule, no freeze-on-expiry. This is the core TOFU-poisoning defense in the spec and it's structurally absent, not just incomplete.
3. expired_ts first-assignment-wins isn't implemented — and this is new since your last review. historical_keys.old_verify_keys.extend(filtered_old_verify_keys) does last-write-wins on Rust's BTreeMap::extend. The collision check right above it only compares key bodies (existing_old_key.key != new_old_key.key), never expired_ts. So two responses with the same key body but different expired_ts sail straight through the collision check and the second one silently overwrites the first via .extend() — precisely the backdating bug we just closed in the spec text this session.
4. Storage ceiling counts active + retired together. total_keys = verify_keys.len() + old_verify_keys.len(); if total_keys > 3000 { evict } — this is the exact "two 3,000s don't reconcile" issue we fixed in the spec a few commits ago, except baked into the implementation the other way: the spec now explicitly exempts active keys from the 3,000, and this code doesn't.
5. Duplicate-key scan is scoped too narrowly. check_no_duplicate_json_keys only walks verify_keys and old_verify_keys as named sections. The spec requires rejecting duplicates "at any depth, anywhere in the response document" — a duplicate top-level server_name or something nested in signatures wouldn't be caught here.

Worth flagging, lower confidence:

6. Backoff growth is already exponential in current code: record_backoff multiplies msc4499_backoff_secs by 1x, 2x, 4x, etc. and caps at 1 hour.

## Q: is the rejection-flag model bloated? (yes)

`EventMetadata` carries 3 independent status booleans (`is_outlier`, `rejected`,
`soft_failed`) + 2 reason strings (`rejection_reason`, `soft_fail_reason`) +
`pdu_count` (None = outlier, i.e. already redundant with `is_outlier`) +
`short_state_hash` (separate state-res concern).

`pdu_metadata` exposes ~14 read/write/take methods over them:
`is_event_rejected`, `is_event_soft_failed`, `is_event_accepted`,
`is_event_visible_to_clients`, `is_event_permanently_rejected`,
`is_event_pending_auth_resolution`, `mark_event_rejected`,
`mark_event_rejected_skip_visibility_check`, `unmark_event_rejected`,
`unmark_event_soft_failed`, `take_retry_if_rejection_retryable`,
`take_retry_if_rejection_retryable_for_promotion`, `mark_as_referenced`,
`is_event_referenced`.

The last ~35 commits touching pdu_metadata/metadata.rs are ALL this class:
promotion TOCTOU, stale-marker inference, retryable-vs-permanent, typed
RejectionCode, batched promotion races, etc. That is the "flag madness".

## Q: would EventStatus enum reduce complexity + lines + improve perf? (yes, all four)

Collapse the status booleans + reasons into ONE typed field:

    enum EventStatus {
        Pending,                  // outlier, awaiting validation
        Accepted,                 // validated (timeline or accepted outlier)
        Rejected(RejectionCode),  // typed, permanent vs retryable in the variant
        SoftFailed(String),
    }

- Complexity: single source of truth; "stale marker on a timeline event" becomes
  IMPOSSIBLE because Accepted/Rejected are mutually-exclusive variants.
- Lines: ~14 methods collapse into `matches!(status, Accepted)` + a few transition
  fns (validate/reject/soft_fail/promote); the ~35 recent fix commits become moot.
- Perf: today every is_* is a separate metadata read + bincode deserialize, and
  is_event_permanently_rejected additionally STRING-parses rejection_reason into
  RejectionCode on each read. Enum stores typed RejectionCode directly → one read,
  no parse, fewer DB round-trips.
- Removes redundancy: is_outlier already implied by pdu_count==None.

Cost: it's a DB migration (EventMetadata is bincode in RocksDB; EventMetadataV1
fallback already exists so the migration path is proven). Large surface. Do it as
its own focused PR — NOT bundled with the test fix or the HAMT work.

## Q: do LtHash / HAMT / state-accumulator reduce this? (mostly no — different layer)

- msc4511/augmented-hamt: DELETES state_compressor (-546 lines), replaces with
  state_hamt + lthash. Real SIMPLIFICATION of state STORAGE. Does NOT touch
  rejection flags.
- msc4500/state-accumulator: EXPANSION (server_pool +643, new endpoint, ~800 lines
  admin/yolo outlier/rejected tooling). Adds layers, doesn't simplify.
- Neither touches event VALIDATION (rejection flags / promotion / sync /send).
  That needs the EventStatus enum (+ optionally Synapse-style staging+background).

Verdict: EventStatus is the single highest-leverage simplification available; it's
orthogonal to HAMT/LtHash (state storage). Both are worth doing, separately.

Here is what each item means in practice. I'm explaining from the review comments and the agents' reports, not from fresh code reading.

1. Profile watcher is still global
- src/service/sync/watch.rs makes every /sync session watch the whole userprofileupdate_value map, using an empty prefix.
- Any user's display name, avatar or profile-field change wakes every active sync on the server. Most of those wakeups find nothing the session is allowed to see and are thrown away.
- On a busy server that is wasted work for every profile edit.
- Fix: subscribe only sessions whose filter asks for profile fields. Alternatively, scope the wake-up to users who share a room with the syncing user. It's a performance issue, not a correctness one.

2. Profile backfill migration
- Custom profile fields are now announced to clients through an update-record stream. Records are written only when a field changes.
- Fields set before this change have no record. A client doing an initial MSC4429 sync won't see them until someone edits them again.
- Fix: a one-time, repeatable migration that writes an update record for every existing field. Or make initial sync read the current profile rows directly instead of the stream.
- Cost: this is a correctness gap for existing users, but only for the MSC4429 initial-sync feature.

3. Strict accessor callers
- The old state accessors silently skip any state event whose PDU can't be loaded. A caller then sees a partial room state and treats it as the whole thing.
- I added strict versions that return errors. Only theesponses and reconcile_membership were moved over.
- About a dozen other callers still use the lossy versof them cache or serve the result, which is where apartial snapshot does harm. Callers that just display
- Next step: audit those callers and move the risky on

4. del_node race
- del_node removes a HAMT node from the database and from an in-memory cache.
- A reader that loaded the node just before the delete after the delete. The cache then holds a node with no
  database row.
- I reordered it to delete the row first and evict the window but doesn't close it.
- Closing it needs a lock or a version counter around
- Risk: this only matters if nodes are deleted while rderstand to be the garbage-collection sweep. It should rare and low-impact.

If you want me to pick one, the strict-accessor audit se it's the only one that can serve wrong data. Theprofile backfill is next, for existing users.
